# Decisions

The general decisions behind how Bonded is built, and why. Change a decision by editing its row and saying why in the pull request.

## Product and tooling

| # | Question | Decision |
|---|---|---|
| 1 | What does the library promise? | **Connections that stay up.** Reconnection in the foreground, in the background and after the system relaunches the app is the core of the library, not an add-on. |
| 2 | Which Nitro? | **Nitro Modules v1**, pinned to an exact version. It brings Swift Package Manager support. |
| 3 | Minimum versions | React Native ≥ 0.88 and iOS ≥ 16, both required by Nitro v1 (Xcode with Swift 6.4); New Architecture only; Android minSdk follows React Native's default, 24 in 0.88. Features of newer Android versions are checked at runtime. |
| 4 | API style | One manager, with devices addressed by ID, because IDs survive background restoration. Promises for operations; typed `onX(callback)` events that return a subscription; one subscription per characteristic, with `remove()`; values as `ArrayBuffer`. Example: `ble.connect(id, { autoReconnect: true })`, `ble.read(id, service, char)`, `ble.subscribe(id, service, char, cb)`, `ble.onConnectionStateChange(cb)`. |
| 5 | Error model | Every failure throws one `BleError` with a shared `code` (`bluetoothOff`, `unauthorized`, `deviceNotFound`, `notConnected`, `connectionFailed`, `disconnected`, `timeout`, `pairingRequired`, `gattError`, `cancelled`, `unsupported`, `unknown`, `valueTooLong`, `characteristicNotFound`, `alreadySubscribed`), the raw `platformCode` (`CBError`/`CBATTError`, Android GATT status), `deviceId` and `operation`. The diagnostics stream carries the same fields. |
| 6 | Android background strategy | Bonded ships its own minimal foreground service of type `connectedDevice` (never `dataSync`, which Android 15 caps at 6 hours a day) as a separate internal Kotlin module with no Bluetooth code. It starts from native code, so Companion Device Manager can wake the app before JavaScript runs; its notification text and icon come from the config plugin; apps can switch it off and run their own. `ble.associate()` opens the Companion Device Manager pairing dialog; reconnection uses presence observation where an association exists and the foreground service alone otherwise. |
| 7 | Bonding API | Part of the core API. `createBond(id, { trigger: { service, characteristic } })` (Android: an explicit bond; iOS: reads the encrypted characteristic to start pairing), `getBondState(id)` (`bonded`/`bonding`/`none` on Android, `unknown` on iOS), `removeBond(id)` (Android only, through a hidden API, documented as best-effort; iOS throws `unsupported`), `onBondStateChange(cb)` (Android). Missing encryption throws `pairingRequired`. |
| 8 | Event stream for diagnostics | **Off by default**, for developers testing their app: nothing is recorded or written until `ble.configure({ diagnostics: { enabled: true } })`, and turning it off deletes what was recorded. While on, Bonded records natively, also while JavaScript is suspended in the background, into a ring buffer of the newest events (1,000 by default, `capacity` to change it) saved in batches to a file in the app's private storage, so the record survives the app being killed. `ble.getDiagnostics({ since })` returns the record, `ble.onDiagnosticEvent(cb)` each new event, `ble.clearDiagnostics()` deletes it, and the hook `useDiagnosticEvents({ limit })` shows the newest, stored and live. Every event carries its time and whether the app was in the foreground or the background. Events: Bluetooth state and permission changes, scan start and stop, connection attempts, connected (MTU, timing), disconnected (shared code, platform code, intentional or not), reconnection attempts, bond changes. GATT operations with durations are opt-in (`diagnostics: { gatt: true }`). Metadata only, never characteristic values. Features publish domain events on the event bus (A2) and the `diagnostics` slice records them; while diagnostics are off nothing observes on its behalf. Developer tools, such as a Rozenite inspector, build on it. |
| 9 | Licence | **MIT**, copyright Devsilk. The React Native norm; contributions arrive under MIT too, so no contributor licence agreement is needed. Code adapted from another open-source project keeps its original licence notice. |
| 10 | Expo | A config plugin with the options `bluetoothUsage`, `background` (iOS `bluetooth-central` and restore identifier; the Android foreground service and its permissions), `neverForLocation`, `foregroundService` (notification title and icon) and `companionDevice`. The example and device-test app is a bare React Native app that builds iOS through Swift Package Manager; an Expo example joins it once Nitro v1 builds through CocoaPods, which Expo uses. Expo Go can't load native modules. |
| 11 | Native testing frameworks | iOS: Swift Testing, with a `@Test("…")` display name on every test. Android on the JVM: Kotest `BehaviorSpec`s in given/when/then with Kotest matchers. Android instrumented: JUnit 4 with `kotlin.test` assertions (Kotest has no instrumentation runner), and snake_case names because the dexer refuses spaces below API 30. Architecture: Konsist and layer checks (the foreground service module never imports Bluetooth code). TypeScript: Jest. |
| 12 | Release pipeline | Releases are published by hand from the maintainer's machine with two-factor confirmation. Automated releases (release-please plus npm trusted publishing, with the maintainer as required approver) replace this once there are co-maintainers or frequent releases. |

## Behaviour

| # | Question | Decision |
|---|---|---|
| R1 | What does reconnection do? | `ble.connect(id, { autoReconnect: true })`, default `false`. With `false`, an unexpected drop is reported (`disconnected` with its reason) and nothing else happens. With `true`, iOS issues a new pending connection at once (no timeout; it connects when the device advertises, also in the background); Android tries a quick direct connection with a short timeout, then falls back to `autoConnect=true`, backing off internally after errors such as status 133. After reconnecting, services are discovered again and every active subscription is restored, so callbacks keep firing. Reconnection stops on `disconnect(id)` or bond removal, and pauses while Bluetooth is off or permission is revoked. `onConnectionStateChange` reports `reconnecting` with the attempt number and the last drop's reason. The option can grow into an object (`{ foregroundOnly: true }`) without breaking `true`/`false`. |
| R2 | Several devices at once? | **Yes**, with no limit imposed by Bonded. Android: one GATT operation queue per connection; going past the phone's limit (typically about 7) throws `connectionFailed` with the platform code. Reconnection, subscriptions and diagnostics are per device; one foreground service covers all connections. The reconnection torture test uses two devices to check that one dropping doesn't disturb the other. |
| R3 | Scanning in the background | Full scanning in the foreground; in the background only with a service UUID filter, otherwise `BleError` `unsupported` with an explanation (iOS ignores unfiltered background scans; Android returns nothing with the screen off). A built-in guard for Android's limit of 5 scan starts per 30 seconds: Bonded spaces scan starts and reports the delay in diagnostics. Reconnecting to known devices never needs scanning. |
| R4 | App killed and relaunched | The README documents the limits plainly. iOS relaunches the app in the background after the system kills it, but not after the user swipes it away, until the user opens it again. On Android the foreground service usually survives a swipe, except on some makers (Xiaomi, Huawei, Samsung's sleeping apps; per-maker settings documented), and a force stop disables everything, Companion Device Manager included, until the app is opened. After a relaunch the native side keeps connections and notifications; `await ble.restore()` returns the connected devices; `subscribe` on a characteristic that is already active natively only attaches the callback and delivers the latest value received while JavaScript wasn't running. |

## Architecture

| # | Question | Decision |
|---|---|---|
| A1 | Internal structure | Clean architecture in vertical slices. A native package per platform for everything that doesn't touch Nitro (Swift package `BondedFeatures`; an Android library with its own Gradle build); the Nitro HybridObjects are thin controllers that call use cases. Slices, mirrored on both platforms: `bluetoothState`, `permissions`, `scanning`, `connection`, `gatt`, `bonding`, `background`, `diagnostics`. Layers per feature: `domain` (base library only), `application` (use cases and the interfaces they need), `adapters`, `infrastructure`. A `compositionRoot` wires everything. Enforced by architecture tests: Swift Testing on iOS, Konsist on Android (see docs/architecture.md). |
| A2 | How features depend on each other | Features never import each other. (1) A shared kernel, `shared/domain`, holds only `DeviceId`, `ServiceUuid`, `CharacteristicUuid`, `BleError` and the domain event types; every feature may import it, and it imports nothing. (2) One shared Bluetooth client per platform in `infrastructure/bluetooth` owns the platform objects (`CBCentralManager`/`CBPeripheral`; `BluetoothGatt` with the GATT operation queue), keyed by `DeviceId`, and knows no features; features' adapters use it. (3) Reactions across features go through domain events on an in-process event bus created in the `compositionRoot` (for example, `connection` publishes `DeviceReconnected`, a `gatt` use case restores subscriptions, and `diagnostics` records every event). The bus is a mechanism, not domain, so it lives in `shared/application`, which imports only `shared/domain`. Architecture tests check that a feature imports only `shared/domain`, `shared/application` and its own folders. |
| A3 | Shared logic: twice or once? | **Written twice, in Swift and Kotlin.** `docs/behaviours.md` names every behaviour once; both platforms have a test with exactly that name (Swift Testing display name, Kotest `then`), and a CI check fails when a listed behaviour lacks a test on either platform. Little is truly shareable: error mapping, reconnection and scan spacing are platform-specific, which leaves the state machine and the ring buffer. C++ would add JNI crossings, memory-safety risk in a long-running background process, a third language and a third test setup. It remains an option for large pure code, such as parsers of standard Bluetooth services. |
| A4 | Threading | iOS (Swift 6, strict concurrency): Core Bluetooth runs on Bonded's own serial queue, never the main thread; the shared Bluetooth client is an actor, and the delegate forwards each callback, in order, into it through an `AsyncStream` (an actor running directly on Core Bluetooth's queue would need `DispatchSerialQueue`, iOS 17+, and Bonded supports iOS 16). Use cases are `async` and `Sendable`, domain types are value types, the event bus is an `AsyncStream`, and the package isn't main-actor by default. Android: `BluetoothGattCallback` callbacks go straight to one single-threaded dispatcher per device (`limitedParallelism(1)`); the GATT operation queue is a `Channel` with `withTimeout` on every operation; use cases are `suspend` functions and the event bus a `SharedFlow`. Bridge: Nitro maps `async`/`suspend` to Promises; high-rate notifications reach JavaScript in batches (about every 16 ms). |
| A5 | Nitro boundary and TypeScript layout | One Nitro HybridObject per feature (`BluetoothState`, `Permissions`, `Scanner`, `Connection`, `Gatt`, `Bonding`, `Diagnostics` specs in `src/specs/`), each implemented natively by a thin controller that calls that feature's use cases. TypeScript: `src/specs` (the Nitro contract; imports nothing), `src/api` (the public `ble` object combining the HybridObjects; validation, `BleError`, subscriptions with `remove()`, unpacking batched notifications; imports only `specs`), `src/plugin` (the Expo config plugin; standalone) and `src/hooks`, published as `react-native-ble-bonded/hooks` (imports only `api`; no `react-native` imports). Enforced by ESLint's boundaries rule in CI. |
| A6 | Listeners | Every listener reports the current value at once, then each change, with repeats suppressed (the rule lives once per platform in `shared/application`). Each has a core subscription (`ble.onStateChange`, `ble.onPermissionChange`, returning `{ remove() }`) for code outside React, and a hook in `react-native-ble-bonded/hooks` (`useBluetoothState`, `useBluetoothPermission`, built on `useSyncExternalStore`) for components. One native listener serves every component using a hook. |
| A7 | Permissions | Bonded asks for permissions itself, natively on both platforms, in the `permissions` slice: `ble.getPermissionStatus()`, `ble.requestPermissions()`, `ble.onPermissionChange()`, `ble.openSettings()`. Statuses are react-native-permissions' (`unavailable`, `denied`, `granted`, `blocked`) without `limited`, which Bluetooth doesn't have. On iOS the system prompt appears only on `requestPermissions()` or the first operation that needs Bluetooth; reading the state or the status never prompts, and reports `unauthorized` or `denied` until then. On Android, Bonded records that it has asked, because Android can't otherwise tell "never asked" from "don't ask again". Changes made in the system settings are picked up when the app returns to the foreground. |
| A8 | Scanning | One scan at a time: `const scan = await ble.startScan(options, onDevice)` returns `{ stop(), stopped }`, and starting another replaces it. `useScan(options)` returns `{ devices, isScanning, error, restart }`: each device once with its latest report, in the order first heard so rows never move (`sort: 'signal'` for strongest first), re-rendering at most every 250 ms, without devices unheard for 10 seconds. Both stop after `timeout` (30 seconds by default, `0` for never). By default both ask for permission when it can still be asked and ask to turn Bluetooth on (`autoRequestPermission`, `autoEnableBluetooth`), `startScan` then rejecting with `unauthorized` or `bluetoothOff`, and `useScan` reporting it in `error` and starting by itself once both are fine. `ble.requestBluetoothOn()` shows Android's system dialog; iOS has no public way to turn Bluetooth on. Filters: `services`, `name` (exact, or `startsWith`/`endsWith`/`includes`, matched natively) and `filter`, a JavaScript predicate; all must match; no regular expressions, because Swift, Kotlin and JavaScript differ. Results are plain data with the common fields; `fullAdvertisement: true` adds everything the platform reports. Manufacturer data comes with its company ID split off. An unfiltered scan pauses while the app is in the background and resumes when it returns (R3). Asking for permission and Bluetooth happens in `src/api`, since native features never use each other (A2). |
| A9 | Connections | A device is a handle, `ble.device(id)`, holding only the ID; its `name`, `connectionState` and `lastDisconnect` read the live state, so it never goes stale and every handle for an ID agrees. Other details are methods on demand (`getServices()`). `await device.connect()` resolves once services are discovered, so `connected` means ready. It waits for the device to advertise (no scan for a known device), stops after `timeout` (30 seconds by default, `0` to wait), resolves at once when connected, shares a running attempt, and is cancelled by `disconnect()`. Like scanning, it asks for permission and to turn Bluetooth on unless switched off. Android's transient failures (GATT status 133 and similar) are retried with a short backoff, first directly, then waiting for the device. Android's workarounds are built in and configurable, globally with `ble.configure({ android })` and per connection: retrying transient errors, closing the GATT client after a disconnection, waiting for pairing before discovery, a pause before discovery on bonded devices, high connection priority during setup, refreshing the service cache, and asking for the largest MTU (517) once connected, so writes without response carry more than 20 bytes as they do on iOS, which negotiates by itself. States: `disconnected`, `connecting`, `connected`, `disconnecting`. Disconnect reasons: `requested`, `outOfRange`, `deviceDisconnected`, `bluetoothOff`, `failed`, each but `requested` with a `BleError`. Listeners: `device.onConnectionStateChange` and `ble.onConnectionStateChange` (all devices, tagged with the ID), current state first (A6); hooks `useDevice(id)` and `useConnectedDevices()`. |
| A10 | Remembered devices | Bonded remembers every device after a successful connection (unless `remember: false`), natively and across launches, until the app calls `device.forget()`, which also disconnects but keeps the system's pairing. Apps store no IDs: `ble.connect()` reconnects the remembered device, `ble.connect({ id })` a given one, and `ble.connect({ name, services })` the first that matches a scan. `ble.device()` and `useDevice()` without an ID give the one remembered device; with several remembered, `ble.device()` throws rather than guess, and `useDevice()` gives `undefined` with a warning in development, so a screen never crashes because a second device connected. `ble.getRememberedDevices()`, `useRememberedDevices()` and `device.isRemembered` list them. With each device Bonded keeps how it was found (name, advertised services, manufacturer company ID). When the platform says a remembered device's ID is unknown (iOS changes identifiers after a network reset), Bonded scans for that identity, connects to the one match and remembers it under its new ID, forgetting the old one, which can never connect again; with several matches it rejects instead of guessing. A timeout never starts this search, because a device that doesn't answer is usually off or out of range, and an identical model nearby must not take its place. Android accepts any address, so there the search doesn't run. Finding a device, by filter or again, uses one timeout for scanning and connecting together, and its scan replaces a running one. |
| A11 | Read and write | `device.read(service, characteristic)` resolves with an `ArrayBuffer`; `device.write(service, characteristic, value)` writes an `ArrayBuffer` or `Uint8Array` with response, `{ withoutResponse: true }` without. UUIDs go with every call; short forms work. Both reject at once with `notConnected` unless the device is connected, connecting included: it's the app's job to call them at the right time, and nothing connects behind its back. Before sending, Bonded checks the call against the services discovered at connect and rejects with `characteristicNotFound` or `unsupported`, naming what the characteristic does allow. With response, values up to 512 bytes (Bluetooth's limit) go as a long write when they need to; without, a value longer than the maximum write length rejects with `valueTooLong`, giving both lengths, and is never split: only the app knows whether its firmware puts pieces back together, and asks for it with `writeChunked` (A13). A write without response resolves once the platform has taken the value, waiting for room, so a loop of awaited writes never drops one. A device's refusal is named: `pairingRequired` when the characteristic needs a paired, encrypted connection, otherwise `gattError` with `attError` (`invalidAttributeValueLength`, `applicationError` for firmware codes) and the number in `platformCode`. Each operation times out after 10 seconds by default. A device runs one operation at a time, and an answer reaches its caller only when it names the caller's characteristic; a caller that times out stops waiting at once, but the device's next operation waits for the late answer, Bluetooth's own 30 seconds, or a disconnect, so no answer reaches the wrong caller. On Android, Android's own statuses (0x80–0x8F, such as 133) are named as Android's, not the device's, and a disconnect during an operation is `notConnected`, as on iOS. Diagnostics record operations only with `diagnostics: { gatt: true }`. Every error says what happened, the values involved and what to do. |
| A12 | Subscriptions | `await device.subscribe(service, characteristic, onValue, { onError, onEnd })` resolves once the device has switched notifications on (Bonded picks notify, or indicate when that's all there is) and returns `{ remove() }`. One subscription per characteristic: a second rejects with `alreadySubscribed`, and the app shares the values itself, as with ble-manager and ble-nitro (ble-plx allows several, and removing one silences the rest). A subscription lives until `remove()`, across disconnects: after every reconnect Bonded switches notifications back on and the same callback keeps firing, so the app never subscribes again (R1). `onError` is called only when that fails; the subscription stays and Bonded tries again after the next reconnect. `forget()` removes the device's subscriptions and calls `onEnd`. Values reach JavaScript in batches about every 16 ms (A4), but `onValue` is called once per value, in order. `useNotifications(device, service, characteristic)` returns `isSubscribed`, the latest value and any error, re-rendering at most once per batch; after a failed subscribe it tries again on the next connection. Reconnects and forgotten devices reach the subscriptions as domain events on the event bus (A2). |
| A13 | Maximum write length, chunked writes and signal strength | `device.getMaxWriteLength()` resolves with the most one write carries: the connection's MTU minus 3. The phone and the device agree on the MTU each time they connect, so it's read, never a constant; Android asks for 517 at connect (`android: { mtu }`) and iOS negotiates on its own, so there's no `requestMtu()`. `device.writeChunked(service, characteristic, data, { withoutResponse })` cuts `data` to that length and sends the chunks in order as one operation: no other read or write on the device gets between them, so firmware that puts them back together can rely on that. Splitting is explicit by name, never hidden in `write` (A11). The timeout applies to each chunk, from when it's sent; the first chunk that fails stops the write, and the error carries `chunkIndex` (counting from 0), `chunkCount` and `sentLength`, the bytes the device took before it, also in its message. Empty data resolves without sending. `device.readRssi()` resolves with the signal strength in dBm, connected only, with the operation timeout; `useRssi(device, { interval })` reads it every second by default while connected and keeps the last reading across a disconnect. On iOS the signal strength isn't queued behind other operations; Android allows it only between them. |
