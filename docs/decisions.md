# Decisions

The general decisions behind how Bonded is built, and why. Change a decision by editing its row and saying why in the pull request.

## Product and tooling

| # | Question | Decision |
|---|---|---|
| 1 | What does the library promise? | **Connections that stay up.** Reconnection in the foreground, in the background and after the system relaunches the app is the core of the library, not an add-on. |
| 2 | Which Nitro? | **Nitro Modules v1**, pinned to an exact version. It brings Swift Package Manager support. |
| 3 | Minimum versions | React Native ≥ 0.88 and iOS ≥ 16, both required by Nitro v1 (Xcode with Swift 6.4); New Architecture only; Android minSdk follows React Native's default, 24 in 0.88. Features of newer Android versions are checked at runtime. |
| 4 | API style | One manager, with devices addressed by ID, because IDs survive background restoration. Promises for operations; typed `onX(callback)` events that return a subscription; one subscription per characteristic, with `remove()`; values as `ArrayBuffer`. Example: `ble.connect(id, { autoReconnect: true })`, `ble.read(id, service, char)`, `ble.subscribe(id, service, char, cb)`, `ble.onConnectionStateChange(cb)`. |
| 5 | Error model | Every failure throws one `BleError` with a shared `code` (`bluetoothOff`, `unauthorized`, `deviceNotFound`, `notConnected`, `connectionFailed`, `disconnected`, `timeout`, `pairingRequired`, `gattError`, `cancelled`, `unsupported`, `unknown`), the raw `platformCode` (`CBError`/`CBATTError`, Android GATT status), `deviceId` and `operation`. The diagnostics stream carries the same fields. |
| 6 | Android background strategy | Bonded ships its own minimal foreground service of type `connectedDevice` (never `dataSync`, which Android 15 caps at 6 hours a day) as a separate internal Kotlin module with no Bluetooth code. It starts from native code, so Companion Device Manager can wake the app before JavaScript runs; its notification text and icon come from the config plugin; apps can switch it off and run their own. `ble.associate()` opens the Companion Device Manager pairing dialog; reconnection uses presence observation where an association exists and the foreground service alone otherwise. |
| 7 | Bonding API | Part of the core API. `createBond(id, { trigger: { service, characteristic } })` (Android: an explicit bond; iOS: reads the encrypted characteristic to start pairing), `getBondState(id)` (`bonded`/`bonding`/`none` on Android, `unknown` on iOS), `removeBond(id)` (Android only, through a hidden API, documented as best-effort; iOS throws `unsupported`), `onBondStateChange(cb)` (Android). Missing encryption throws `pairingRequired`. |
| 8 | Event stream for diagnostics | `ble.onDiagnosticEvent(cb)` live, plus `ble.getDiagnostics({ since })` from a native ring buffer (about 1,000 events) that records while JavaScript is suspended in the background. Events: scan start and stop, connection attempts, connected (MTU, timing), disconnected (shared code, platform code, intentional or not, foreground or background), reconnection attempts, bond and Bluetooth state changes. GATT operations with durations are opt-in (`diagnostics: { gatt: true }`). Metadata only, never characteristic values. Developer tools, such as a Rozenite inspector, build on it. |
| 9 | Licence | **MIT**, copyright Devsilk. The React Native norm; contributions arrive under MIT too, so no contributor licence agreement is needed. Code adapted from another open-source project keeps its original licence notice. |
| 10 | Expo | A config plugin with the options `bluetoothUsage`, `background` (iOS `bluetooth-central` and restore identifier; the Android foreground service and its permissions), `neverForLocation`, `foregroundService` (notification title and icon) and `companionDevice`. The example and device-test app is a bare React Native app that builds iOS through Swift Package Manager; an Expo example joins it once Nitro v1 builds through CocoaPods, which Expo uses. Expo Go can't load native modules. |
| 11 | Native testing frameworks | iOS: Swift Testing, with a `@Test("…")` display name on every test. Android on the JVM: Kotest `BehaviorSpec`s in given/when/then with Kotest matchers. Android instrumented: JUnit 4 with `kotlin.test` assertions (Kotest has no instrumentation runner), and snake_case names because the dexer refuses spaces below API 30. Architecture: Konsist and layer checks (the foreground service module never imports Bluetooth code). TypeScript: Jest. |
| 12 | Release pipeline | Releases are published by hand from the maintainer's machine with two-factor confirmation. Automated releases (release-please plus npm trusted publishing, with the maintainer as required approver) replace this once there are co-maintainers or frequent releases. |

## Behaviour

| # | Question | Decision |
|---|---|---|
| R1 | What does reconnection do? | `ble.connect(id, { autoReconnect: true })`, default `false`. With `false`, an unexpected drop is reported (`disconnected` with its reason) and nothing else happens. With `true`, iOS issues a new pending connection at once (no timeout; it connects when the device advertises, also in the background); Android tries a quick direct connection with a short timeout, then falls back to `autoConnect=true`, backing off internally after errors such as status 133. After reconnecting, services are discovered again and every active subscription is restored, so callbacks keep firing. Reconnection stops on `disconnect(id)` or bond removal, and pauses while Bluetooth is off or permission is revoked. `onConnectionStateChange` reports `reconnecting` with the attempt number and the last drop's reason. The option can grow into an object (`{ foregroundOnly: true }`) without breaking `true`/`false`. |
| R2 | Several devices at once? | **Yes**, with no limit imposed by Bonded. Android: one GATT operation queue per connection; going past the phone's limit (typically about 7) throws `connectionFailed` with the platform code. Reconnection, subscriptions and diagnostics are per device; one foreground service covers all connections. The reconnection torture test uses two devices to check that one dropping doesn't disturb the other. |
| R3 | Scanning in the background | Full scanning in the foreground; in the background only with a service UUID filter, otherwise `BleError` `unsupported` with an explanation (iOS ignores unfiltered background scans; Android returns nothing with the screen off). A built-in guard for Android's limit of 5 scan starts per 30 seconds: Bonded spaces scan starts and reports the delay in diagnostics. Reconnecting to known devices never needs scanning. |
| R4 | App killed and relaunched | The README documents the limits plainly. iOS relaunches the app in the background after the system kills it, but not after the user swipes it away, until the user opens it again. On Android the foreground service usually survives a swipe, except on some makers (Xiaomi, Huawei, Samsung's sleeping apps; per-maker settings documented), and a force stop disables everything, Companion Device Manager included, until the app is opened. After a relaunch the native side keeps connections and notifications; `await ble.restore()` returns the connected devices; `subscribe` on a characteristic that is already active natively only attaches the callback and delivers the latest value received while JavaScript wasn't running. |

## Architecture

| # | Question | Decision |
|---|---|---|
| A1 | Internal structure | Clean architecture in vertical slices. A native package per platform for everything that doesn't touch Nitro (Swift package `BondedFeatures`; an Android library with its own Gradle build); the Nitro HybridObjects are thin controllers that call use cases. Slices, mirrored on both platforms: `bluetoothState`, `scanning`, `connection`, `gatt`, `bonding`, `background`, `diagnostics`. Layers per feature: `domain` (base library only), `application` (use cases and the interfaces they need), `adapters`, `infrastructure`. A `compositionRoot` wires everything. Enforced by architecture tests: Swift Testing on iOS, Konsist on Android (see docs/architecture.md). |
| A2 | How features depend on each other | Features never import each other. (1) A shared kernel, `shared/domain`, holds only `DeviceId`, `ServiceUuid`, `CharacteristicUuid`, `BleError` and the domain event types; every feature may import it, and it imports nothing. (2) One shared Bluetooth client per platform in `infrastructure/bluetooth` owns the platform objects (`CBCentralManager`/`CBPeripheral`; `BluetoothGatt` with the GATT operation queue), keyed by `DeviceId`, and knows no features; features' adapters use it. (3) Reactions across features go through domain events on an in-process event bus created in the `compositionRoot` (for example, `connection` publishes `DeviceReconnected`, a `gatt` use case restores subscriptions, and `diagnostics` records every event). Architecture tests check that a feature imports only `shared/domain` and its own folders. |
| A3 | Shared logic: twice or once? | **Written twice, in Swift and Kotlin.** `docs/behaviours.md` names every behaviour once; both platforms have a test with exactly that name (Swift Testing display name, Kotest `then`), and a CI check fails when a listed behaviour lacks a test on either platform. Little is truly shareable: error mapping, reconnection and scan spacing are platform-specific, which leaves the state machine and the ring buffer. C++ would add JNI crossings, memory-safety risk in a long-running background process, a third language and a third test setup. It remains an option for large pure code, such as parsers of standard Bluetooth services. |
| A4 | Threading | iOS (Swift 6, strict concurrency): Core Bluetooth runs on Bonded's own serial queue, never the main thread; the shared Bluetooth client is an actor, and the delegate forwards each callback, in order, into it through an `AsyncStream` (an actor running directly on Core Bluetooth's queue would need `DispatchSerialQueue`, iOS 17+, and Bonded supports iOS 16). Use cases are `async` and `Sendable`, domain types are value types, the event bus is an `AsyncStream`, and the package isn't main-actor by default. Android: `BluetoothGattCallback` callbacks go straight to one single-threaded dispatcher per device (`limitedParallelism(1)`); the GATT operation queue is a `Channel` with `withTimeout` on every operation; use cases are `suspend` functions and the event bus a `SharedFlow`. Bridge: Nitro maps `async`/`suspend` to Promises; high-rate notifications reach JavaScript in batches (about every 16 ms). |
| A5 | Nitro boundary and TypeScript layout | One Nitro HybridObject per feature (`BluetoothState`, `Scanner`, `Connection`, `Gatt`, `Bonding`, `Diagnostics` specs in `src/specs/`), each implemented natively by a thin controller that calls that feature's use cases. TypeScript: `src/specs` (the Nitro contract; imports nothing), `src/api` (the public `ble` object combining the HybridObjects; validation, `BleError`, subscriptions with `remove()`, unpacking batched notifications; imports only `specs`), `src/plugin` (the Expo config plugin; standalone) and `src/hooks`, published as `react-native-ble-bonded/hooks` (imports only `api`; no `react-native` imports). Enforced by ESLint's boundaries rule in CI. |
